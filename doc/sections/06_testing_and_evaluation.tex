\section{Testing and Evaluation}
\label{sec:testing_and_evaluation}

\subsection{Object Detection and Tracking Performance}

\paragraph{Object detection performance.}

Object detection metrics were evaluated using the held-out test split of the
ABODA dataset, which was not included in the training data. Note that the
training and test splits originate from the same dataset, so the model has been
exposed to the same visual domain during fine-tuning
(section~\ref{sec:training_process}), though not the specific test images. The
performance of the YOLO26 model was assessed using standard object detection
metrics, including mean Average Precision (mAP) at various Intersection over
Union (IoU) thresholds.

The test split comprised $111$ images containing $202$ annotated instances
($99$ person, $103$ luggage). Table~\ref{tab:detection_results} summarises the
per-class results.

The model achieved an overall mAP@0.5 of $0.859$, with both classes performing
comparably. Luggage detection slightly outperformed person detection in both
precision ($0.898$ vs.\ $0.884$) and recall ($0.845$ vs.\ $0.788$), suggesting
the fine-tuning phase successfully adapted the model to luggage instances in
surveillance contexts.

The precision-recall curve (figure~\ref{fig:pr_curve}) shows that both classes
maintain high precision ($>0.9$) up to approximately $0.6$ recall before
degrading. The confusion matrix (figure~\ref{fig:confusion_matrix}) reveals
that inter-class confusion is minimal, only $2\%$ of true luggage instances are
misclassified as person. The primary source of error is background false
positives, where $55\%$ of background regions trigger person predictions and
$45\%$ trigger luggage predictions. In the context of the downstream pipeline,
these false positives are mitigated by the tracker's temporal consistency
requirements, which filter out transient spurious detections.

The relatively small test set ($111$ images) means these metrics should be
interpreted with caution, as individual images can disproportionately influence
the results.

\paragraph{Limitations of object tracking evaluation.}

The object tracking component of the pipeline was unable to be quantitatively
evaluated due to the absence of frame-level annotations for the target domain
test set. The idea of running semi-automated annotation for a MOTA-style ground
truth using the object detection model was tested but ultimately abandoned due
to the infeasible amount of manual correction required to produce a reliable
ground truth. As a result, the evaluation of the tracking component was limited
to the context of the pipeline as a whole, with the focus on the abandonment
logic over the tracking performance in isolation.

\subsection{Validation Protocol for Abandonment Logic}

Due to the unavailability of frame-level annotations for the test set, a
temporal event-based ground truth was established. An event was defined by a
single temporal anchor (the frame of abandonment) and a spatial region of
interest (ROI). The pipeline was evaluated using a temporal tolerance of $\pm
	360$ frames ($\approx 12$ seconds depending on the frame rate) to account for
manual annotation variability and the system's hysteresis.

\subsubsection{Ground Truth Annotation Methodology}
\label{sec:ground_truth_annotation_methodology}

Due to the temporal nature of abandoned luggage, traditional frame-by-frame
bounding box annotations were impractical. Instead, the ground truth was
established using a single-point event anchoring method.

For each video in the dataset, the annotation process followed these steps:

\begin{enumerate}
	\item \textbf{Scene Triage and Parameter Definition}
	      \begin{itemize}
		      \item Reviewal of the entire video sequence to determine if a genuine abandonment
		            event has occurred, setting the \texttt{has\_abandonment} flag accordingly.
		      \item Based on the camera's perspective, focal length, and requirements of the
		            scenario, definition of the spatial and temporal limits for that specific
		            video; i.e., determining the radius of ownership and the temporal window for
		            abandonment detection as \texttt{radius\_px} and \texttt{threshold\_s}
		            respectively.
	      \end{itemize}
	\item \textbf{Event Anchoring}
	      \begin{itemize}
		      \item If an abandonment event is identified, the annotator scrubs through the video
		            to identify the exact moment the bag transitions from being unattended to being
		            abandoned.
		      \item Calculate the frame number corresponding to this moment, by determining where
		            the owner breaches the ownership radius, and then moving forward in time by the
		            defined threshold to anchor the event.
		      \item This frame number is then recorded as the \texttt{true\_abandon\_frame}. This
		            metric acts as the temporal anchor against which the pipeline's detection
		            latency is measured.
		      \item If there a multiple events that occur in the same video, multiple anchors are
		            committed to the ground truth, with the spatial parameters remaining the same.
		            This allows for the evaluation of more complex sequences.
	      \end{itemize}
	\item \textbf{Negative Sample Logging}
	      \begin{itemize}
		      \item If the video contains no abandonment event (e.g., a bag is left unattended but
		            the owner returns within the defined temporal threshold), the video is tagged
		            with \texttt{has\_abandonment} set to \texttt{false}. The frame and ROI fields
		            are left null.
		      \item Negative samples are useful for testing the pipeline's resilience against false
		            positives.
	      \end{itemize}
\end{enumerate}

Annotations are saved in a structured \texttt{JSON} format
(listing~\ref{lst:annotation_format}), producing a comprehensive ground truth
dataset that is strictly tied to the logic of the abandonment detection
pipeline.

\subsubsection{Datasets Used for Validation}

Annotations were performed on the eleven examples from the ABODA dataset
mentioned in section~\ref{sec:suspicious_luggage_dataset}. These examples, the
ground truth annotations derived from them, and the annotation script
(section~\ref{sec:annotation_script}) can be found in a forked repository at
\url{https://github.com/maxnaro/ABODA}. The resulting annotated dataset
consisted of eleven samples with one or more abandonment events. The IITP20
dataset's $55$ video examples, the singular AVSS example and their annotations
are not included in the repository in order to respect the original datasets'
licensing terms but were also used in the evaluation process.

\paragraph{Limitation: training and evaluation domain overlap.}

Because ABODA frames were included in the fine-tuning training data
(section~\ref{sec:training_process}), the end-to-end pipeline evaluation on
ABODA video sequences is not fully independent of the training domain. While
the object detection test split was held out from training, the pipeline-level
evaluation uses the original ABODA videos, which contain frames the detector
may have seen during training. This overlap means that pipeline results on
ABODA may overstate the system's generalisation to truly unseen surveillance
footage. The IITP20 and AVSS results, where no training overlap exists, provide
a more reliable measure of out-of-domain performance.

\subsubsection{Evaluation Script}

With an established ground truth, an evaluation script was developed to run the
pipeline, directly on the deployment hardware, against the test examples and
compare the pipeline's abandonment detections with the ground truth.

An \texttt{EventLogger} class was implemented to capture discrete abandonment
events from the pipeline's output; detected events are matched against the
ground truth event using the $\pm 360$ frame temporal tolerance to classify
detections as TP, FP, FN, or TN (see
section~\ref{sec:evaluation_metrics_for_object_detection},
table~\ref{tab:evaluation_metrics_desc}). The resulting logging output
comprising of the number of events per class, frame error and IoU per video.

During processing, the script takes periodic snapshots of the systems resource
usage via the \texttt{jtop} utility. This allows for the evaluation of the
pipeline's computational efficiency while processing the test videos, providing
insight into the system's performance under load.

Once the script has processed all test videos, the logged events are aggregated
to produce performance metrics for the pipeline. The metrics include:
precision, recall, and F1-score at the event level --- mean IoU and mean frame
error for the run as a whole; metrics are calculated using the formulae
outlined in section~\ref{sec:evaluation_metrics_for_object_detection},
table~\ref{tab:evaluation_metrics_formula_1}.

\paragraph{Limitations.}

The evaluation script is designed to be run on the deployment hardware,
providing a realistic assessment of the pipeline's performance in its intended
environment. However, it is limited by the fact that it can only evaluate the
pipeline on the specific test videos for which ground truth annotations have
been established. Additionally, the script's reliance on temporal event
matching means that it may not capture nuances in detection timing or spatial
accuracy beyond the defined tolerance thresholds.

Evaluations were performed on hardware without the display sink component of
the pipeline active. This significantly reduces the time taken to run the
pipeline (as videos can be processed at a much faster rate than real-time) but
means that the evaluation results do not account for any performance impact of
the display sink, which is a component of the deployed system. Anecdotally, the
display sink was observed to have a neg.ligible impact on the pipeline's
performance, not compromising real-time performance, but this was not formally
evaluated.

Expectedly, the pipeline performed the best on the ABODA examples, given the
training domain overlap (section~\ref{sec:training_process}). The majority of
video examples exhibited no false alarms on the background, with the logic
filtering noise well in the absence of any confounding factors.

The main sources of error were: ``video2'', which features a steep overhead
angle, and ``video11'', which features a crowded scene with a far-away camera
angle. ``video11'' is the main outlier of the dataset with no other examples
matching its level of complexity, and demonstrated that the pipeline's logic is
not robust enough to handle crowded scenes with significant occlusion and
smaller detection sizes. ``video2'' saw the model struggle to detect the
ownership consistently, with the tracking component losing the owner and
misidentifying another person as the owner, which caused the abandonment event
to be missed. The two examples demonstrate the limitations of the pipeline's
logic from a detection and tracking perspective, where logic is unable to
compensate for the ReID model's lack of domain generalisation in the case of
``video2'', and the inference model's performance limitations in crowded scenes
in the case of ``video11''.

Metrics were generally strong across the ABODA examples, with a high precision
of $0.750$ and recall of $0.800$ at the event level. The mean frame error of
$197.9$ frames ($\approx 6.6$ seconds) is higher than ideal, but this is
influenced by the fact that some events were detected significantly later than
the ground truth anchor, which may be due to the system's hysteresis.

The GPU was consistently the bottleneck, sustaining $86$--$90\%$ average
utilisation across all runs, with peaks reaching near $100\%$. CPU utilisation
remained moderate ($\approx 29\%$ average), confirming that the pipeline's
computational load is predominantly on the GPU as expected for a
TensorRT-accelerated inference workload. RAM usage was stable at $70$--$73\%$,
leaving sufficient headroom for the operating system and other processes.

Temperatures remained well within the $85\degree\mathrm{C}$ throttling
threshold, peaking at $65\degree\mathrm{C}$ during the longest run (IITP20
medium, $41$ minutes). The absence of any thermal throttling across nearly $93$
minutes of cumulative processing confirms that the Jetson Orin Nano can sustain
the pipeline workload without performance degradation with the default cooling
solution.
