\section{Implementation}

\subsection{Dataset Procurement}

\subsubsection{Object Detection Dataset}

The training dataset for the object detection model was sourced from the
Microsoft COCO dataset \citep{lin2014microsoft}. As mentioned prior, the COCO
dataset is a large-scale source of over $200,000$ labelled images across 80
object categories. The entirety of the dataset would lead to rundandancy with a
majority of classes being out of scope for the target application. Therefore, a
subset of the COCO dataset was created, containing only images including the
\texttt{person}, \texttt{backpack}, \texttt{handbag} and \texttt{suitcase}
classes, which I then aggregated into a single \texttt{luggage} class. This
resulted in a training dataset of $8,887$ images split into training and
validation splits of $8,397$ and $490$ images, respectively. This split ensured
that the validation set contained a representative sample of the training data,
allowing for an accurate assessment of the model's performance during training
and optimisations whilst the training set provided a sufficient amount of data
for the model to learn from.

Originally, I had intended to use datasets specific to the abandoned luggage
detection domain, such as ABODA, however these datasets failed to include the
amount of variation needed for training a robust model. Many annotated
datasets, created from the source footage, led to overfitting and poor
generalisation on test examples due to their smaller size, limited diversity in
viewpoints, and repeated scene context. The COCO dataset, while lacking the
domain specificity, offers a much larger variety of examples, covering a wide
range of environments, lighting conditions, and object appearances.

Another benefit of using the COCO dataset is the ease of access and
availability of annotations that are compatible with the latest YOLO models. A
python script was used to filter the COCO dataset, specify the YOLO annotation
format, balance class instances, remap classes to a single \texttt{luggage}
class, and oversample specific classes (\ref{sec:model_training_optimisation})
to create a more varied and proportionate training dataset.

Constructing the dataset programmatically allowed for a specific and
reproducable balance between the detected classes, which is crucial in the
context of abandoned luggage detection, where smaller objects such as bags may
be underrepresented in typical dataset. The target \texttt{person} budget was
constrained by $N_{\text{person},\text{allowed}}=r\cdot N_{\text{luggage}}$,
where $r$ is the target class instance ratio. Utilising balancing and
oversampling techniques resulted in an overall class instance ratio of
$\frac{13092}{6543} \approx 2.0:1$ between the \texttt{person} and
\texttt{luggage} classes shown in
figure~\ref{fig:dataset_class_distribution_after}; the reasoning behind this
method is covered in more detail in the model training and optimisation section
(\ref{sec:model_training_optimisation}). An example of the class distribution
of the dataset before and after the balancing and oversampling techniques were
applied is shown in figures~\ref{fig:dataset_class_distribution_before} and
\ref{fig:dataset_class_distribution_after}, respectively.

Oversampling was applied to the consituent classes of the \texttt{luggage}
class, which inferred upon review of the model's performance. This was
implemented by duplicating images containing the underrepresented classes,
defined by a parameter assigning weights to each class e.g.,
``\texttt{backpack=2,handbag=3,suitcase=1}'' for the given COCO classes. This
method allowed the model to learn the features of more difficult classes, such
as \texttt{handbag}s, which it struggled to detect in the early stages of
training.

A limitation of using the COCO dataset and the sampling techniques used is the
inherent lack of domain specificity, whilst the dataset contains a wide variety
of examples, its lack of CCTV-native footage can lead to models struggling to
generalise to the target application. Aggregating multiple classes into a
single \texttt{luggage} class can also lead to a loss of granularity in the
model's understanding of different types of luggage, however, this is a
necessary trade-off to ensure a sufficient amount of training data was
available and for the model to learn a more generalised representation of
luggage which can help with the issue of generalisation.

\subsubsection{Suspicious Luggage Dataset}

The purpose of the suspicious luggage dataset is to provide a source of data
for testing the end-to-end DeepStream pipeline, not for training the primary
detector. This dataset is important for validating the temporal logic, tracking
consistency, and alert behaviour of the system in realistic scenarios.

The coverage of the dataset was focused on scenarios relevant to the target
application, including people and luggage items that are abandoned, moving, or
in close proximity to each other. An ideal dataset would include a variety of
environments, conditions and factors such as occlusion, lighting, and crowd
density to ensure the robustness of the system. The dataset should also include
a sufficient number of examples of each scenario to allow for a comprehensive
evaluation of the system's performance as outlined in the requirements analysis
section (\ref{sec:requirements_dataset_procurement_preparation}).

A mixture of positive and negative cases were sourced to evaluate the system's
ability to correctly identify suspicious luggage while minimising false
positives; positive cases including true abandonment and negative cases
including stationary luggage with the owner nearby, brief separations, and
occlusions.

Example datasets for suspicious luggage scenarios were sourced from the ABODA
dataset (\url{https://github.com/kevinlin311tw/ABODA}), containing $11$ video
sequences of various environments and scenarios. These videos were used for the
testing and evaluation of the suspicious luggage detection pipeline, with
examples featuring marked changes in lighting condition, nighttime scenarios,
indoor and outdoor environments.

In addition, authors \citet{amin2021large} provide a dataset of scenarios split
into abandoned and non-abandoned scenarios, with graded levels of difficulty.
This dataset has been used in literature by authors
\citet{abandoned2025vrsalovic}.

Unfortunately, the PETS2006 \citep{thirde2006pets} and AVSS-2007
\citep{qmul2007avss} datasets were unable to be sourced despite their
prevalence in the literature and my efforts to contact the authors. The
utilisation of AVSS-2007 was restricted to a single example video sequence,
which was used in conjunction with the aforementioned procured datasets.

\subsection{Model Training and Optimisation}
\label{sec:model_training_optimisation}

Model training (and export, see section~\ref{sec:model_export}) was separated
into its own submodule for version control which can be found at
\url{https://github.com/maxnaro/luggage-watch-training/}.

\subsubsection{Training Environment}

Once the training dataset was procured and prepared, the next step was to train
the model and optimise its performance. The training environment involved a
containerised setup using Docker, with leveraging NVIDIA's GPU support for
accelerated training. Training, being separate to deployment, allowed for a
more flexible and powerful environment, enabling the use of the greater
computational resources of a desktop GPU and system as a whole. The hardware of
the training system can be found in the appendix (\ref{sec:training_hardware}).

The containerised approach allowed for a consistent and reproducible training
environment, with dependency management and isolation from the host system.
Containers require some overhead, but less than virtual machines, and the
benefits of consistency and ease of setup outweighed the performance cost in
this case.

The training script was implemented using Ultralytics' YOLO training framework,
which offered a high-level API for training YOLO models, built-in support for
various optimisers such as AdamW \citep{loschilov2017fixing}, and an automatic
optimiser which chooses based on other configuration parameters; data
augmentation techniques, and easy integration with the procurred dataset. The
training script was used in conjunction with a custom configuration file
specifying the parameters of the training process as seen in
listing~\ref{lst:config}.

\subsubsection{Training Process and Iterative Optimisation}

A transfer learning approach was applied where a pre-trained YOLO model was
fine-tuned on the custom dataset. This approach allows the model to leverage
the general features learned from the large-scale COCO dataset, which can be
beneficial for improving performance and reducing training time, especially
when the custom dataset is relatively small. The pre-trained model used in the
final iteration was \texttt{yolo26s.pt}, a compact and efficient model
architecture, well suited for deployment on edge devices like the NVIDIA Jetson
Orin Nano.

Model training was an iterative process, with multiple rounds of training and
evaluation to optimise the model's performance. Training a YOLO model involves
adjusting various hyperparameters such as learning rate, batch size, number of
epochs and augmentation strategy. Feedback from validation performance was used
to guide each optimisation step, with the goal of improving mAP@0.5,
mAP@0.5:0.95, precision and recall
(section~\ref{sec:evaluation_metrics_for_object_detection}). Although all
metrics were considered, recall was prioritised because false negatives (missed
detections) are operationally more severe than false positives in suspicious
luggage detection.

An early baseline run used \texttt{yolo11l.pt} at \texttt{imgsz=640}, with
\texttt{optimizer=auto}, \texttt{lr0=0.01}, \texttt{batch=16}, no backbone
freezing, and uncached loading. A later optimised run used \texttt{yolo26s.pt}
at \texttt{imgsz=1280}, \texttt{optimizer=AdamW}, \texttt{lr0=0.001},
\texttt{batch=0.8} (auto-scaled by available VRAM), \texttt{freeze=10}, and
\texttt{cache=disk}. The rationale behind these changes was: (i) increase input
resolution to improve small-object localisation for luggage items, (ii) improve
optimisation stability with AdamW and a lower initial learning rate, (iii)
preserve transferable low-level visual features by freezing early backbone
layers, and (iv) improve training throughput and memory efficiency using disk
caching and adaptive batch sizing at higher resolution.

Another additional optimisation step that was applied was the use of early
stopping with a patience of $30$ epochs, which allows the training process to
stop early if the validation metrics do not improve for the specified number of
epochs. This can help to prevent overfitting and reduce training time. For
example, in another training run, the model was trained for $100$ epochs with
early stopping enabled, and the training process stopped at epoch $87$ when the
validation metrics plateaued (see figure ~\ref{fig:plateau_map5095}),
indicating that the model had likely converged and further training would not
yield significant improvements. This optimisation step can be particularly
beneficial when training on a limited dataset, as it helps to avoid overfitting
and ensures that the model generalises well to unseen data.

Furthermore, data augmentation techniques were applied during training to
improve the model's generalisation capabilities. These techniques included
random horizontal flipping, scaling, and color jittering (all implemented
natively by the \texttt{auto\_augment} feature of the framework), which help
the model to learn invariant features and improve its robustness to variations
in the input data. Data mosaicing, a technique where multiple images are
combined into a single training example, was also applied to further enhance
the diversity; mosaicing was disabled in the last 10 epochs to allow the model
to fine-tune on simpler examples as it converged.

contains $37$ epochs with final metrics of mAP@0.5:0.95 $=0.2645$, mAP@0.5

completed $100$ epochs with final metrics of mAP@0.5:0.95 $=0.3951$, mAP@0.5

this corresponds to approximately $+49.4\%$ mAP@0.5:0.95, $+47.7\%$ mAP@0.5,

\subsection{Model Export}
\label{sec:model_export}

The result of training is a PyTorch model checkpoint file, which contains the
learned weights and architecture information. However, for deployment on the
NVIDIA Jetson Orin Nano, the model needed to be exported to a format compatible
with NVIDIA's TensorRT inference engine, which is optimised for performance on
proprietary hardware. The export process involved converting the PyTorch model
to ONNX format, which is a widely supported intermediate representation for
machine learning models.

Exporting the model to ONNX format was achieved using the same containerised
environment as training, utilising a custom export script sourced from
``DeepStream-Yolo'' GitHub repository \citep{luciano2026deepstreamyolo}, which
provides DeepStream SDK implementations for YOLO models. Since I had planned to
use DeepStream, and by extension \citeauthor{luciano2026deepstreamyolo}'s
\texttt{nvdsinfer} custom implementation for YOLO models, using
\citeauthor{luciano2026deepstreamyolo}'s export script ensured compatibility
and optimised performance when deploying the model.

The containerised export implementation forwards parameters into the
DeepStream-compatible YOLO26 exporter. The exporter applies model-level changes
required for compatibility with downstream DeepStream parsing: the detection
head is switched to export mode, output formatting is adapted for ONNX export,
and the final tensor is transformed into a compact per-detection layout of
\texttt{[x1, y1, x2, y2, score, class\_id]}. A \texttt{labels.txt} file is also
emitted from the trained class names to preserve class-index alignment at
inference time.

The main export configuration used in this project is summarised in the
appendix~\ref{sec:config}, with the key parameters being: \texttt{format=onnx}
to specify the export format, and \texttt{imgsz=1280} to maintain the input
resolution used during training.

In practice, this produced an ONNX model suitable for subsequent TensorRT
engine generation on the Jetson platform while retaining compatibility with the
DeepStream YOLO parser.

\subsection{Deployment Setup and Configuration}
\label{sec:deployment_setup_and_configuration}

The deployment system used an NVIDIA Jetson Orin Nano running JetPack 6.2 and
DeepStream 7.1 to perform real-time inference using the trained model, and
integrating the object tracking and abandonment logic into an end-to-end
pipeline.

Steps to set up the deployment environment included: (i) installing the
necessary software dependencies in order to run a Python-based DeepStream
application, (ii) compiling the custom YOLO parser library from
\citet{luciano2026deepstreamyolo} to enable support for the exported model, and
(iii) downloading the Re-ID model from NVIDIA's TAO Toolkit Model Zoo, which is
used for object tracking and re-identification in the pipeline.

Development of the inference application was done using Python, and was
contained as submodule in the repository at
\url{https://github.com/maxnaro/luggage-watch-inference} which was able to be
cloned and worked on directly on the Jetson device via SSH.

\subsection{DeepStream Pipeline Configuration}

The implementation of the DeepStream pipeline involved the instantiation of a
series of GStreamer elements, responsible for the different stages of video
processing, object detection, tracking and abandonment logic. These elements
were configured and linked together to form a cohesive pipeline that processes
video input, performs inference using the trained model, and outputs the
results in realtime. The configuration was defined programmatically in the
Python application in listing~\ref{lst:pipeline} and is represented in
figure~\ref{fig:pipeline}.

Iterative development and testing of the pipeline was performed using
pre-recorded video sequences from the procured suspicious luggage dataset,
which which allowed for debugging of the pipeline's functionality, the
generation of TensorRT engine files, and validation of inference performance on
the target hardware before implementing the rest of the system's logic and
deployment.

Configuration for the primary object detection stage of the pipeline is
determined by a custom configuration file, which specifies parameters such as
the model path, input resolution, confidence threshold, and class count. These
parameters can have a significant impact on the performance of the model and
the overall system, and were tuned based on the results of the developing and
testing process. The configuration file can be found in the appendix
~\ref{lst:primary_config}, with the reasonings for the key parameters being:

\begin{itemize}
	\item \textbf{Inference Interval and Real-time Tradeoff:} The
	      \texttt{interval} parameter, which specifies the number
	      of frames to skip between inferences, was set to $3$
	      to balance the tradeoff between inference performance and real-time
	      processing. Using a lower interval (e.g., $1$) would allow for more
	      frequent detections but in practice led to increased latency and
	      reduced frame rates, while a higher interval reduced the computational
	      load at the expense of missing brief events. Ultimately, an interval
	      of $3$ was found to provide a good balance for the target application,
	      as the temporal logic of the system is designed to detect abandoned luggage over a
	      span of several seconds, so missing detections in a few frames does
	      not significantly impact the overall performance.
	\item \textbf{Aspect Ratio and Padding Behaviour:} The \texttt{maintain-aspect-ratio}
	      parameter was set to \texttt{1} (true) to ensure that the aspect ratio of the input
	      is maintained during resizing, along with the \texttt{symmetric-padding} being set
	      to \texttt{1} (true) to apply symmetric padding when resizing. This configuration was chosen to
	      preserve the spatial relationships between objects in the input frames, which is important for
	      accurate detection and tracking. Furthermore, the reduced distortion allowed the
	      model to detect smaller luggage items more effectively.
	\item \textbf{TensorRT Engine Generation and Compatibility:} The \texttt{model-engine-file}
	      parameter specifies the path to the TensorRT engine file generated from the exported ONNX model
	      specified at \texttt{onnx-file}. If no engine file can be found, the system will attempt
	      to generate one from the ONNX file which, while time-consuming, only has to be done once.
	      This engine file is optimised for inference on the NVIDIA Jetson Orin Nano, having
	      been generated on the device itself, and ensures compatibility with the DeepStream pipeline.
	      Additionally, the \texttt{network-mode} parameter is set to \texttt{2} to specify FP16
	      precision for the engine, providing the benefits outlined in
	      sections~\ref{sec:real_time_processing_on_edge_devices} and \ref{sec:tensorrt_optimisations}.
	\item \textbf{Custom Parsing Implementation for YOLO Models:} The parameters,
	      \texttt{parse-bbox-func-name}, \texttt{custom-lib-path}, and \texttt{engine-create-func-name},
	      specify the custom C++ parsing implementation for YOLO models provided by \citet{luciano2026deepstreamyolo}.
	      This enables the exported YOLO model to be correctly parsed and integrated into the DeepStream pipeline,
	      ensuring that the detections are correctly interpreted and processed by the subsequent elements in the pipeline.
\end{itemize}

\subsection{Object Tracking Integration}

Object tracking is a crucial component of the system, allowing for the
consistent identification of objects across frames, which is essential for the
temporal logic of abandoned luggage detection. The tracking component was
implemented as a \texttt{nvtracker} element of the pipeline using the
\texttt{NvDeepSORT} algorithm.

\subsubsection{Determining the Optimal Tracking Algorithm}

The choice of tracking algorithm was informed by a combination of researching
current implementations
(\ref{sec:video_analysis_spatio_temporal_modeling_and_object_tracking}),
determining the solutions used by similar projects in the literature (e.g.,
ByteTrack \citep{zhang2022bytetrack} used by \citet{abandoned2025vrsalovic}),
and practical testing of different algorithms on the target hardware. Luckily,
the modular design of the DeepStream pipeline allowed for relatively easy
integration and testing of different tracking algorithms, as they can be
swapped out as different configurations passed to the \texttt{nvtracker}
element.

The available options from the DeepStream SDK included: \texttt{IoU Tracker},
using the IoU values among detections to associate them across frames;
\texttt{NvSORT}, an implementation of the SORT algorithm
\citep{bewley2016simple} which uses a combination of bounding box proximities
for association and a Kalman filter to update the state of tracked objects;
\texttt{NvDeepSORT}, an extension of SORT that incorporates a deep association
metric \citep{wojke2017simple} and a Re-ID model for association;
\texttt{NvDCF}, an implementation that uses a discriminative correlation filter
for tracking; and \texttt{MaskTracker}, mainly used for segmentation tasks.

After testing the different algorithms, it became clear that the requirements
of the system required a robust tracking solution. Environmental factors such
as occlusion and crowd density whilst using a less rigorous tracking algorithm
led to frequent ID flips and ownership misattribution, which in turn led to
incorrect abandonment detections. The requirements for ownership and ID
consistency across frames, made \texttt{NvDeepSORT} the most suitable choice,
as its use of a deep association metric and Re-ID model provided improved
robustness to occlusion and appearance changes, which are common in
surveillance scenarios.
